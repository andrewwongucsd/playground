# playground

A record of building and operating a small multi-product web platform on real
production infrastructure — a Go game server, two React frontends, and the
Terraform, Kubernetes, and CI/CD that puts them on a managed cloud cluster
with TLS, a database, and continuous backups.

This repository is a **write-up, not the source** — it documents the
architecture, the engineering decisions, and the failures worked through
along the way. It intentionally contains no application code.

## What was built

Two products behind one cluster:

| Product | What it is | Stack |
| --- | --- | --- |
| **Multiplayer card game** | Real-time [Big Two](https://en.wikipedia.org/wiki/Big_two) — a pure rules engine, a WebSocket server with matchmaking and bot fill-in, and a browser table UI. Practice scoring only, no wagering. | Go (engine + server), React + TypeScript |
| **Developer utilities toolbox** | Nine browser-only tools: a JSON/YAML tree editor, Base64/URL/JWT, regex tester, hash & UUID, timestamp & cron, QR codes, a WYSIWYG Markdown editor, a thumbnail grabber, and an image converter. No backend. | React + TypeScript |

Both run on a single always-free ARM node in a managed Kubernetes cluster,
behind one load balancer, on automatically-renewed TLS.

The game's frontend and API share one hostname on purpose: the browser derives
its WebSocket URL from the page origin, so one image runs on any hostname, the
login-session cookie is first-party, and CORS never engages in production.

## How it's operated

- **Everything is infrastructure-as-code.** The cluster, its network (a VCN
  with separate public-endpoint, private-worker, and public-load-balancer
  subnets), the node pool, and every IAM identity are provisioned with
  Terraform. Nothing was clicked into existence in a console.
- **Least-privilege service identities, generated by Terraform.** Three
  separate machine identities, each with keys created in Terraform and never
  typed by hand: a narrow per-push deploy identity scoped by Kubernetes RBAC
  to a few resource kinds in two namespaces; a distinct cluster-admin identity
  used only by a manually-dispatched workflow; and a backup identity that can
  write to exactly one storage bucket and nothing else. A leak of the routine
  deploy credential can touch nothing cluster-wide.
- **First-party manifests with Kustomize, third-party add-ons with Helm** —
  the standard split. The ingress controller, certificate manager, and
  database operator are each installed via their own officially-supported
  Helm charts; the application manifests are Kustomize overlays.
- **CI/CD gated on a vulnerability scan.** Every image is built for the
  cluster's ARM architecture, scanned for critical/high CVEs *before* it is
  allowed to reach the registry, then deployed — with the pipeline blocking on
  the rollout actually succeeding, not just on the API accepting it.
- **The database is backed up continuously**, not just snapshotted: the
  write-ahead log is streamed to S3-compatible object storage, which is what
  makes point-in-time recovery possible.

## A note on scope

The card game is deliberately practice-scoring only — no wagering, no payout,
no cash-out anywhere in its API surface. That is a considered boundary, not an
unfinished feature.
